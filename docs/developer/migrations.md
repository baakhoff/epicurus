# Schema migrations

How a database change ships. Schema is **Alembic-managed, one migration environment per
service**, applied in-process when the service starts (#834, ADR-XXXX). This page is the
working reference: what to do when you change a model, what happens at startup, and what the
gates prove.

> **Not every service is migrated yet.** `storage` is the reference; the other store-owning
> services are being converted one at a time and meanwhile still use the additive reconcile
> described in [`db` reference](../reference/db.md). `task migrate:list` tells you which
> services are migration-managed today.

## The short version

You changed a column, added a table, or renamed something:

```bash
task migrate:new -- storage "add etag to storage_files"   # writes the next revision, empty
# edit services/storage/src/epicurus_storage/migrations/versions/0002_add_etag_to_storage_files.py
task migrate:check -- storage                             # models vs. revisions, ~1 second
```

`migrate:check` upgrades a throwaway SQLite database from empty to head and then runs
`alembic check`: if the models and the revisions disagree it fails and names the difference.
CI's **`migrations`** job runs the same comparison against real Postgres, plus the upgrade paths
SQLite cannot stand in for — so a model change with no revision does not merge.

Revisions are **hand-written**, not autogenerated. Autogenerate needs a live Postgres holding
the *previous* schema, which the [docker-light local setup](testing.md) does not have, and a
revision guessed against SQLite renders DDL that is wrong on Postgres. `migrate:new` gives you
the file, the revision id and the parent link; you write the `op.*` calls, and `migrate:check`
proves they land where the models say.

## Why it is per service

Every service shares **one** Postgres database (`DATABASE_URL` points at `…/epicurus` in every
`services/*/compose.yaml` and in the chart) and owns **disjoint tables** in it — not its own
schema. Three consequences shape the whole design:

- **A version table per service**: `alembic_version_storage`, `alembic_version_core_app`, … A
  single shared `alembic_version` would have seven services overwriting each other's head
  revision, and the first one to start would "downgrade" the rest.
- **Autogenerate is filtered to the service's own tables.** Unfiltered, each service would see
  the other six services' tables as present-but-not-in-my-models and propose dropping them, and
  `alembic check` could never pass. The filter lives in
  [`epicurus_core.db.alembic_env`](../reference/db.md#alembic_env).
- **Revision ordering is per service.** Two services never share a history, so two lanes can
  each add a revision without a merge conflict or a branched head.

A service also has one engine but **many** `DeclarativeBase` objects — one private base per
store module (`core-app` has 28). So the migration target is a *list* of `MetaData`, declared
once in the service's `migrations/__init__.py`.

## What a service's migration environment looks like

```
services/storage/src/epicurus_storage/migrations/
  __init__.py                 SERVICE, SCRIPT_LOCATION, METADATAS
  env.py                      three lines: `from … import run; run()`
  versions/
    0001_baseline.py          the schema as it stood at adoption
    0002_<slug>.py            every change since, in order
```

It lives **inside the package**, not at `services/<name>/alembic/`. The service image is built
with `uv sync --no-editable --package epicurus-<name>`, which installs the wheel hatchling
assembles from `src/<package>` and nothing else — a migration directory outside that tree would
pass every test and every CI job and then be missing from the running container.

There is **no `alembic.ini`**. The configuration that matters (the live connection, the metadata
list, the version table) cannot live in a static file; it is passed through `Config.attributes`
by `epicurus_core.db.migrations.alembic_config`, and `scripts/migrate.py` is the entry point for
every chore. Running the bare `alembic` CLI against this tree is not supported.

`__init__.py` imports only its service's **store modules** — never the app — so loading it needs
no settings, no database and no network. That is what lets the generator and the CI gate
describe a service without booting it.

## What happens at startup

The service's lifespan calls `run_migrations` once, before anything reads or writes a row:

```python
from epicurus_core.db.migrations import run_migrations
from epicurus_storage.migrations import METADATAS, SCRIPT_LOCATION


@asynccontextmanager
async def lifespan(_: FastAPI) -> AsyncIterator[None]:
    await run_migrations(
        engine, service=MODULE_NAME, script_location=SCRIPT_LOCATION, metadatas=METADATAS
    )
    ...
```

**In the lifespan, not a separate init step.** A container has one entry point on both runtimes
the stack supports: Compose has no init-container concept, and giving the Helm chart one would
put the schema behind a code path Compose never executes — the opposite of the Kubernetes
parity rule. One in-process call runs identically on both.

**Concurrency is handled, not assumed away.** The chart can scale a module past one replica
(`core-app` is a singleton, modules are not), and Compose can start a new container while the
old one is still coming up — so two processes can reach `upgrade head` together. `run_migrations`
takes a Postgres **session-level advisory lock** keyed on the service name, on a connection of
its own, for the duration. The loser waits, then finds nothing to do. The key is a BLAKE2b hash
of `epicurus:db:migrations:<service>` folded into a signed 64-bit integer — deliberately not
Python's `hash()`, which is salted per interpreter, so two replicas would derive different keys
and neither would ever wait. Off Postgres (the unit tests, on SQLite) there is no lock and no
concurrency, and the runner says so at DEBUG.

Alembic runs through `connection.run_sync(...)`, so the service's existing asyncpg engine is the
only database driver it needs.

The runner logs which of three states it found — this is the line to read in a startup log:

| Logged `database=` | What it means |
| --- | --- |
| `fresh` | No version table, none of this service's tables: a new deployment. |
| `adopted` | This service's tables exist but no version table — a database built by the pre-Alembic `create_all`/reconcile path, now coming under management. |
| `managed` | A version table exists; an ordinary upgrade, usually a no-op. |

Classification is for the log only. **There is one code path:** `upgrade head`, in all three
cases. See the next section for why that is safe.

## The baseline revision is idempotent

A baseline is generated from the models as they stand the day a service adopts Alembic, so it
describes a schema that on every already-running deployment *already exists*. A plain
`op.create_table` would fail on exactly the databases that matter most.

The alternative — stamp the baseline as applied, then upgrade from there — needs a separate
"is this a pre-Alembic database?" branch, and it is **wrong** the moment a deployment skips the
adoption release: the stamp swallows every revision in between, including a backfill the stamp
cannot perform. (That is #903's fix, so it is not hypothetical.)

So the baseline itself is idempotent. It is rendered against
[`epicurus_core.db.ops`](../reference/db.md#ops) rather than Alembic's `op`:

```python
from epicurus_core.db import ops as ep


def upgrade() -> None:
    ep.create_table(
        "storage_files",
        sa.Column("id", sa.Integer(), nullable=False),
        sa.Column("source", sa.String(length=16), server_default=sa.text("'fs'"), nullable=False),
        sa.PrimaryKeyConstraint("id"),
    )
    ep.create_index(ep.f("ix_storage_files_tenant"), "storage_files", ["tenant"], unique=False)
```

`ep.create_table` creates the table when it is absent, and when it is already there runs the
audited additive reconcile over the columns declared in the call — adding whatever the live
table lacks, with the same rules the pre-Alembic path used. `ep.create_index` adds an index the
table does not have and skips one it does. One `upgrade head` therefore serves an empty
database, a database built by the old reconcile, and a database already at head, with no branch
anywhere and no revision ever skipped.

**Only the baseline is written this way.** Every revision after it is ordinary Alembic —
`op.add_column`, `op.alter_column`, an `UPDATE` for a backfill — because after adoption the
database's state is known exactly.

What the reconcile arm deliberately does *not* do: add a constraint, or alter a column that is
already present. A table that exists but carries no unique constraint is beyond an additive
repair, and inventing a `DROP`/`ALTER` inside a baseline would make it destructive on databases
nobody has inspected. Such a case gets its own revision, where it is explicit and reviewable.

## Generating a baseline (a service lane adopting migrations)

```bash
uv run python scripts/migrate.py baseline <service>
task migrate:check -- <service>
```

The generator diffs the service's models against an **empty in-memory SQLite** database and
renders the result. That sounds like a portability hazard and is not: from empty the only
operations autogenerate can produce are `create_table` and `create_index`, and those are
rendered from the *model metadata*, never from reflection — so nothing about the connected
dialect reaches the output. **Server defaults were the one exception**, and they are handled
explicitly, because Alembic's own renderer gets them wrong in two ways that only show up when
the revision runs:

- a literal default (`server_default="'fs'"`) is rendered with its quotes **stripped**, so
  SQLAlchemy emits the bare SQL token `fs` — a column reference on Postgres, not a string;
- a function default (`server_default=func.now()`) is rendered **pre-compiled against the
  connected dialect**, so a baseline generated on SQLite would freeze SQLite's
  `(CURRENT_TIMESTAMP)` into a migration that then runs on Postgres.

The generator renders a literal as `sa.text("<the string, verbatim>")` and `func.now()` as
itself, and **refuses to render anything else** rather than guessing. If you add a new kind of
server default, teach `scripts/migrate.py:_render_server_default` about it — a wrong default is
invisible until production.

Read the rendered file before committing it. Types that would differ between SQLite and Postgres
are the thing to look for; the repo currently uses `String(n)`, `Text`, `Integer`,
`BigInteger`, `Float`, `Boolean`, `DateTime(timezone=True)` and `JSON`, all of which render
dialect-neutrally from metadata. A dialect-specific type (`postgresql.JSONB`, an array) would
render as `postgresql.JSONB()` and needs the import added by hand, plus a second look.

A baseline is written **once**; the generator refuses to overwrite an existing `versions/`.

## Expect the gate to fail on `server_default="'…'"` — and what to do

**Every service still carrying a plain-string `server_default` will fail its first `migrations`
run, on the adoption arm.** This is a real defect the gate surfaces, not a gate bug, and each
lane fixes it the same way.

A *plain string* `server_default` is a **literal SQLAlchemy quotes for you**, not raw SQL. So the
house pattern `server_default="'fs'"` compiles to `DEFAULT '''fs'''` — a default whose value is
the four characters `'fs'`, quotes included:

```text
server_default="'fs'"        ->  DEFAULT '''fs'''     (value: 'fs'  — wrong)
server_default=text("'fs'")  ->  DEFAULT 'fs'         (value: fs    — intended)
server_default="0"           ->  DEFAULT '0'          (a quoted zero)
```

The additive reconcile pasted the same string into `ALTER TABLE … ADD COLUMN` as **raw SQL** and
produced `DEFAULT 'fs'`. So a table created fresh and a table that gained the column through the
reconcile have disagreed about their own default for as long as both paths have existed. Nothing
noticed because inserts set these columns explicitly and the row-readers coerce anything
unexpected to the intended value — but the defaults in the database are wrong, and only a
migration can fix them.

The fix, per service:

1. Change the model to `server_default=text("'…'")` (keep the quotes — `text()` means "this is
   SQL"). Do **not** drop to the bare `server_default="fs"`: the reconcile would then emit
   `DEFAULT fs`, which is a column reference.
2. Write a revision that normalises an existing database — the default, and any row the old one
   produced. `services/storage/.../versions/0002_normalise_the_storage_files_source_default.py`
   is the worked example: an `op.execute` for the rows, then an `alter_column` **inside
   `op.batch_alter_table`** (SQLite has no `ALTER COLUMN` at all, so the batch block is what
   makes the revision runnable under `task migrate:check`).
3. Re-run `task migrate:check -- <service>` and watch the gate's adoption arm.

Columns affected repo-wide: the `"'fs'"` / `"'{}'"` / `"'[]'"` / `"''"` / `"0"` server defaults.
`storage` is done (#926); each remaining lane does its own.

## The backfill rule

The additive reconcile had one documented limit: a column the model marks `NOT NULL` with no
`server_default` cannot be added to a populated table — there is nothing to backfill existing
rows with — so it was added **nullable**, and readers coerced the resulting `NULL` to the
model's Python-side default. That is exactly what #903 was: a `NULL` in a `default=`-only
column aborting a preferences write.

Migrations can fix it properly, so when a service adopts them, **audit its
`default=`-without-`server_default=` columns** and write a revision for each one that the model
marks `NOT NULL`:

```python
def upgrade() -> None:
    op.execute(
        "UPDATE module_prefs SET suggestions_enabled = true WHERE suggestions_enabled IS NULL"
    )
    op.alter_column(
        "module_prefs",
        "suggestions_enabled",
        server_default=sa.text("true"),
        nullable=False,
    )
```

The `UPDATE` first (so `SET NOT NULL` can succeed), then the `server_default` so new rows and
any future reconcile get it too. A column inside a unique constraint needs care: backfilling
several rows to the same value can collide, so decide what the value should be per row rather
than blanket-defaulting.

Inventory at the time of writing: **`storage` has none** — its one post-release column (`source`)
carries a literal `server_default`. `calendar` has seven (`calendar_events.all_day`,
`calendar_events.excluded`, `calendar_sync_state.collection`,
`calendar_synced_event.{collection,title,all_day,change_hash}`); the other services have not been
audited yet. Each service lane audits its own and says so in its PR.

## SQLite, Postgres, and what each gate proves

Production is Postgres. The unit tests are SQLite, and there are two places that matters:

- **`render_as_batch=True`** in the shared `env.py`. SQLite cannot `ALTER` much of anything, so a
  revision that alters a column has to run inside a batch block (copy to a new table, move the
  rows, swap the names). Write such a revision with `op.batch_alter_table(...)` and it runs on
  both; on Postgres batch mode compiles down to the plain `ALTER` it would have emitted anyway.
  The *baseline* is deliberately not rendered in batch mode — batch wraps `create_index` in a
  `batch_alter_table`, which bypasses the idempotent shim.
- **A test builds schema from the models, not from the revisions.** `FileIndex.init()` and its
  equivalents still call `create_all`, because an Alembic run per test is needless cost. That is
  only honest because the gates below prove the two agree; without them `init()` would be a way
  to add a column and never notice the deployment does not have it.

| Gate | What it proves |
| --- | --- |
| `task migrate:check -- <service>` (local, ~1s) | Upgrade from empty on SQLite, then `alembic check`: the models and the revisions agree. |
| **`migrations`** (CI, Postgres 17, ~2 min) | The same on real Postgres, plus: a second run is a no-op; a `create_all`-built database is adopted and still matches its models; and a *drifted* pre-Alembic database — the columns the reconcile was responsible for stripped out first, the #214 / #218 state — is repaired by the baseline. Each arm runs on a throwaway database of its own. |
| `runtime-smoke` / `k8s-smoke` (CI) | The fresh-install path for real: both boot the stack from an empty Postgres, so a baseline that does not apply fails them. |

The `migrations` job discovers services by glob (`services/*/src/*/migrations/env.py`) inside
`scripts/migrate.py` — never from a list in the workflow — so a service lane adopting migrations
is covered from its own commit with no workflow edit.

**`migrations` is not a required check until it has run green for two weeks**, the bar
`k8s-smoke` was held to (#894). Until then a red here is a signal to read, not a merge block —
but never merge one without reading it.

## Adding migrations to a service that does not have them yet

The service template ships no store, so there is nothing to scaffold — see
[Building a module](building-a-module.md#a-store-and-its-schema) for the recipe a module with a
store follows. In outline:

1. `services/<name>/pyproject.toml`: depend on `epicurus-core[db]`, not bare `epicurus-core`
   (the extra is what puts Alembic in the image; SQLAlchemy the store already declares).
2. Add `src/<package>/migrations/__init__.py` exporting `SERVICE`, `SCRIPT_LOCATION` and
   `METADATAS` — one entry per store module's `DeclarativeBase`. **A store module left out of
   `METADATAS` is a store whose drift nothing detects.**
3. Copy `env.py` verbatim from `storage`; it is three lines and identical for every service.
4. `uv run python scripts/migrate.py baseline <name>`, then read the rendered revision.
5. Call `run_migrations` from the lifespan, before any store's `init()`; delete the
   `ensure_columns` calls and `_ADDED_COLUMNS` lists from the stores (the baseline absorbed
   them), and leave `init()` as `create_all` for the tests.
6. Audit the backfill rule above and write a revision per affected column.
7. `task migrate:check -- <name>`, and watch the `migrations` gate on the PR.

## Downgrades

A generated baseline has a real `downgrade()` that drops the service's tables, and later
revisions should reverse themselves where they can. Nothing automatic ever runs a downgrade —
the startup path only ever goes to head. Treat `alembic downgrade` as a deliberate, data-losing
operation, and take a [backup](../infrastructure/backup-and-restore.md) first.
